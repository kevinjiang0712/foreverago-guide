# 后续怎么维护

你只需要描述看见的问题和期望结果。AI 负责定位文件、修改、验证和记录本地版本。
完整提示词见 [maintain-site.md](../prompts/maintain-site.md)。

## 三种常见修改

| 想做什么 | 通常修改哪里 |
|---|---|
| 改导航分类、主题、语言或官方链接 | config |
| 改游戏显示名、新文章、首页文案、实体资料、翻译、图片 | content、public/media |
| 修手机布局、筛选、地图、动画或生成逻辑 | src、scripts |

不要直接编辑 `.generated` 或 `.next`。它们会在内容准备或构建时重新生成。

## 描述问题的最短格式

> 在【页面网址】，使用【手机/电脑】，做【操作】后，出现【实际结果】。
> 我希望【期望结果】。保持当前模板的设计规范，修复后给我本地预览和验证结果。

不确定问题在哪一层也没关系。例如：

> 这个站的手机导航文字被截断了。先定位原因，保持现有设计规范，修复后给我看本地预览，并说明修改了框架、配置还是内容。

## 每次修改怎么留下回退点

让 AI 先检查当前站的 Git 状态，保留当前修改，再开始修复。完成后做本地提交并告诉你提交编号。
需要撤销时，直接说“撤销刚才这次修改，保留之后我自己改过的内容”，让 AI 先检查差异再处理。
不要使用会直接丢弃全部未提交内容的命令。

## 什么检查能说明什么

- 内容检查通过：文件格式、ID、引用及发布规则合法。
- 构建通过：当前内容能够生成页面。
- 浏览器检查通过：检查过的屏宽和操作实际可用。
- 本地通过不表示网站已经部署，也不表示搜索引擎已经收录。

修改配置、文章或素材时，开发预览会自动更新。修改框架里的内容 schema 或生成逻辑后，应重启开发服务，避免开发进程继续使用旧校验规则。

## 浏览器验证的首次准备

第一次运行浏览器检查时，先安装测试浏览器：

```bash
npx playwright install chromium
```

随后按修改范围运行：

```bash
npm run verify:site
npm run test:browser
```

`verify:site` 构建并检查当前站真实内容生成的页面；`test:browser` 在系统临时目录中使用固定样例 A 测试框架交互，使用独立构建目录和测试服务，不替换当前站的内容。测试服务默认占用 3199；端口已被其他程序使用时会报错，不会终止那个程序。

如果已安装可用的 Chrome，也可以设置 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` 指向它的完整可执行文件路径。`TEST_BASE_URL` 只供维护人员明确指定已有测试服务；普通框架测试无需设置。

## 独立站之间的关系

每次新建站都是一份独立项目，有自己的配置、文章和 Git 历史。母模板之后改进，不会自动更改已经建立的站。
如果要把某次修复带到另一个站，明确告诉 AI 要同步哪个修复和目标目录；先检查两站差异，分别验证和提交。
